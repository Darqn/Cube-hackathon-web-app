# Запуск Cube на Ubuntu VPS

Эта конфигурация находится в ветке `deploy/ubuntu-vps`, созданной от проверенной объединённой версии `e8bef13`. Основная ветка не изменяется. Новое улучшение механического OCR из `feature/meter-ocr` (`347b328`) в эту версию ещё не перенесено; здесь работает Tesseract OCR объединённой ветки.

Понадобятся Ubuntu с доступом по SSH, 2 vCPU / 4 ГБ RAM, желательно 50 ГБ диска, публичный IPv4 и открытые входящие TCP 80/443. SSH 22 ограничьте своим адресом в группе безопасности Selectel. Конфигурация публикует только порты HTTPS-прокси; PostgreSQL и API доступны внутри Docker-сети.

## 1. Установка

Все команды ниже выполняются **в SSH-терминале на Ubuntu**. При первом входе смените пароль root, если он оказался на опубликованном скриншоте.

```bash
sudo apt-get update
sudo apt-get install -y git python3 curl ca-certificates
git clone --branch deploy/ubuntu-vps --single-branch https://github.com/Darqn/Cube-hackathon-web-app.git
cd Cube-hackathon-web-app
sudo bash scripts/install-docker-ubuntu.sh
```

Installer использует официальный Docker apt repository для вашей версии Ubuntu. Уже установленный Docker с Compose v2 сохраняется. Для существующей установки без Compose plugin скрипт остановится с указанием причины; существующие контейнеры автоматически не удаляются.

## 2. HTTPS без покупки домена

В панели Selectel скопируйте публичный IPv4 **этого сервера**. Например, для адреса `203.0.113.10` техническое имя было бы `api.203.0.113.10.sslip.io`. Этот пример — служебный адрес из документации; введите свой настоящий IP:

```bash
read -r -p 'Публичный IPv4 сервера из Selectel: ' CUBE_PUBLIC_IP
sudo bash scripts/vps.sh init "api.${CUBE_PUBLIC_IP}.sslip.io"
```

[sslip.io](https://sslip.io) возвращает IP, указанный в имени. Услуга не требует регистрации. Caddy автоматически запрашивает и продлевает сертификат для технического имени. HTTP 80 и HTTPS 443 должны быть доступны извне; выпуск сертификата требует корректного DNS и доступа к центру сертификации. Возможны ограничения DNS-провайдера и лимиты выдачи сертификатов. Позже можно подключить собственное имя, изменив `CUBE_API_HOST` в `deploy/vps/.env` и повторив запуск.

Настройки генерируются в `deploy/vps/.env` с правами `600` и двумя независимыми случайными паролями БД. Файл игнорируется git. Повторный `init` сохраняет существующие настройки и завершается без перезаписи: случайная смена паролей уже созданной БД нарушила бы подключение.

## 3. Сборка и запуск

```bash
sudo bash scripts/vps.sh start
sudo bash scripts/vps.sh bootstrap
sudo bash scripts/vps.sh status
```

Первый запуск собирает .NET 10.0.403 / ASP.NET Core 10.0.14 образ с настоящим Tesseract. SDK нужен только внутри стадии сборки, устанавливать .NET на VPS не требуется. Версии .NET/NuGet и миграции проекта сохранены.

`start` запускает PostgreSQL, применяет существующие миграции отдельным контейнером и затем поднимает API и Caddy. API работает от непривилегированного пользователя ОС и отдельного пользователя БД без superuser/createdb/createrole. Только контейнер миграций получает подключение владельца БД. Обычный API-процесс не получает его пароль. Служебные аккаунты БД создаются при инициализации новой, отдельной БД deployment; бизнес-схема и существующие миграции не меняются.

`bootstrap` интерактивно запрашивает логин, email и пароль первого администратора. Пароль вводится без отображения и не передаётся как значение аргумента командной строки. Минимум 12 символов, верхний/нижний регистр, цифра и специальный символ. Повторное создание администратора в уже настроенной БД будет отклонено.

Caddy может потребоваться время на первый сертификат. Проверка с вашего компьютера или VPS:

```bash
curl "https://api.${CUBE_PUBLIC_IP}.sslip.io/health/ready"
```

Ожидается `{"status":"Ready"}`. После нового SSH-подключения переменную `CUBE_PUBLIC_IP` нужно ввести заново либо подставить готовое имя из `deploy/vps/.env`. Это адрес backend; web/mobile клиент запускается отдельно. OpenAPI в Production не публикуется.

Контейнеры имеют `restart: unless-stopped` и запускаются вместе с Docker после перезагрузки VPS. БД, файлы, Data Protection keys и данные сертификатов сохраняются в отдельных именованных volumes.

## 4. Подключение клиента Expo

На **своём компьютере**, в PowerShell, укажите настоящий адрес API:

```powershell
cd tenant-app-frontend
$env:EXPO_PUBLIC_API_URL = 'https://api.ВАШ_IP.sslip.io/api/v1'
npm ci
npx expo start --lan --clear
```

Замените `ВАШ_IP` публичным IPv4 VPS. Metro будет выводить Expo QR, а приложение станет обращаться к удалённому backend. Текущий `start-cube.bat` предназначен для локального/LAN API и перезаписывает `EXPO_PUBLIC_API_URL`, поэтому для этого режима используйте команду выше. Собранный клиент тоже должен получить этот URL при сборке.

Для web-клиента с другим origin задайте его точный адрес в `CUBE_WEB_ORIGIN` внутри `deploy/vps/.env`, например `https://portal.example.ru`, и повторите `start`. Начальные CORS origins: localhost:8081 и 127.0.0.1:8081. Нативные приложения не используют браузерный CORS; авторизация API обязательна в обоих случаях.

## 5. Обслуживание и ограничения

```bash
sudo bash scripts/vps.sh logs
sudo bash scripts/vps.sh status
sudo bash scripts/vps.sh stop
```

`logs` показывает API и Caddy; Ctrl+C завершает просмотр. `stop` останавливает контейнеры, сохраняя данные. Для последующего старта используйте `start`. Новые версии приложения сначала проверьте, затем выполните `git pull --ff-only` в этой ветке и `start`. Перед миграциями существующей рабочей БД сделайте резервную копию и изучите изменения.

Для ошибки сертификата проверьте DNS имени, публичный IP, TCP 80/443 в Selectel/системном firewall и логи Caddy. Для ошибки готовности проверяйте также логи БД. PostgreSQL не нужно публиковать в интернет.

Если Docker сообщает о пересечении подсетей, выберите свободную частную `/24` сеть через `CUBE_SUBNET` и входящий в неё адрес прокси через `CUBE_PROXY_IP` в `deploy/vps/.env`. Начальные значения — `172.30.231.0/24` и `172.30.231.10`. API доверяет forwarded headers только этому адресу и локальному healthcheck. Поддержка proxy по умолчанию выключена для остальных способов запуска.

Файлы в Production остаются `Quarantined`: действующий scanner workflow ещё требуется подключить, прежде чем документы/вложения станут доступны пользователям. Development-обход на этом VPS не включается. Реальные платежи, Email, 1С и Битрикс остаются отключены. Резервное копирование БД и файлов, контроль диска, мониторинг, обновления ОС и проверка восстановления выполняются отдельно; один VPS не обеспечивает отказоустойчивость.

Копию `deploy/vps/.env` и резервные копии volumes храните защищённо вне этого VPS. Перезапуск контейнера и резервное копирование решают разные задачи.

## Проверка конфигурации

`ReverseProxyTests` проверяют принятие HTTPS/client IP только от явно доверенного proxy, игнорирование поддельных заголовков и отключённый по умолчанию режим. Тесты существующих контрактов продолжают проверять прежние API и EF snapshot.

Workflow `Ubuntu VPS deployment` собирает настоящий Dockerfile и запускает `scripts/test-vps.py` на Ubuntu 24.04. Smoke test создаёт собственный уникальный Compose project, БД и volumes; проверяет TLS с доверенным локальным CA Caddy, HTTP redirect, authentication, Production OpenAPI, настоящий OCR, карантин, ограниченную роль БД, non-root API и сохранность сессии/файла после пересоздания контейнеров. Затем удаляет только временные ресурсы этого теста. Публичный выпуск сертификата для Selectel проверяется уже на вашем IP после запуска.
