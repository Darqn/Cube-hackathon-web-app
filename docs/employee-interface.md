# Рабочий кабинет сотрудника компании

Кабинет расположен в том же frontend, что и панель администратора и кабинет арендатора. После входа пользователя с серверной ролью `Staff` открывается `/staff/overview`. Роль выбирается администратором при создании учётной записи, а не пользователем на экране входа.

## Запуск и создание доступа

```bash
# Корень репозитория: после обновления исходников нужно пересобрать backend
scripts/dev.sh setup
bash scripts/dev-web.sh

# Другой терминал
cd tenant-app-frontend
npm ci
npm run web -- --clear --port 8081
```

Первый администратор создаётся через `scripts/dev.sh bootstrap` с защищённо заданными переменными `Bootstrap__Login`, `Bootstrap__Email`, `Bootstrap__Password`. Стандартных логинов и паролей нет.

Администратор открывает **Пользователи и роли → Создать сотрудника**, задаёт ФИО, логин, email и пароль. Затем в **Маршрутизации** назначает сотрудника ответственным за категорию либо в карточке конкретного обращения выбирает ответственного и срок.

Направления из ТЗ: аренда, электричество, водоснабжение и отопление, строительство, бухгалтерия, расторжение аренды. Новые обращения категории автоматически назначаются её ответственному внутри приложения. Изменение маршрутизации не переназначает старые обращения. Если ответственный отсутствует, обращение остаётся у администратора до назначения.

## Разделы и ежедневная работа

| Раздел | Возможности |
| --- | --- |
| Обзор | Новые, активные, просроченные и ожидающие уточнения обращения; ближайшие сроки; назначенные направления; счётчики непрочитанных событий и показаний на проверку |
| Обращения | Только назначенные сотруднику задачи; поиск по теме, организации, помещению и контактам; фильтры по статусу, категории, организации, помещению, новым событиям, просрочке и срокам на сегодня; сортировка по сроку и дате; страницы по 20 записей |
| Карточка обращения | Контактное лицо, организация, помещение, срок, защищённые вложения, переписка с авторами и временем, история статусов, публичные ответы и внутренние заметки |
| Уведомления | Назначения, изменения сроков и статусов, сообщения арендаторов и сотрудников, новые показания по направлению; отдельные прочитанные/непрочитанные состояния; переход к записи; отметка одного или всех доступных событий |
| Счётчики | Только электрические/водяные приборы по назначенной ответственности; организация, помещение, номер, единицы, текущее значение и история |
| Показания | Очередь проверки, фильтры по прибору и результату; предыдущее/новое значение, расход, фото; принять или отклонить с обязательным комментарием |
| Мой профиль | ФИО, логин, email и роль; изменение ФИО/телефона; смена пароля с повторным входом |

Карточки обзора открывают соответствующую очередь. Фильтр «Срок сегодня» использует местный часовой пояс браузера. Даты и время отображаются средствами клиентского устройства. Обращения и уведомления обновляются каждые 20 секунд, сводка и показания — каждые 30 секунд, справочник приборов — каждые 45 секунд. Кнопка «Обновить» запрашивает данные немедленно. Это опрос API, а не push-доставка.

## Ответы, файлы и внутренние заметки

В карточке выберите вид сообщения до отправки:

- **Публичный ответ арендатору** — текст и файлы доступны арендатору.
- **Внутренняя заметка сотрудникам** — текст и файлы доступны администратору и текущему ответственному сотруднику. Они исключены из арендаторского ответа API; прямое скачивание внутреннего файла арендатором возвращает 404.

Можно отправить текст, файлы или их сочетание. До 5 файлов в одном ответе, суммарно до 20 МиБ; поддерживаются форматы backend: PDF, JPEG/PNG и проверяемые Office-документы. Загрузка и сообщение сохраняются вместе: некорректный файл не создаёт частичное сообщение. Во время отправки редактор защищён от изменения черновика.

В production новые файлы остаются в карантине до проверки. Ответ сохраняется, но скачивание вложений ожидает разрешения серверного процесса проверки. Интерфейс сообщает об этом. Development-исключение не означает проверку на вредоносное содержимое и не должно использоваться в production.

## Статусы и сроки

Сотрудник меняет статус только назначенного обращения, с указанием причины и актуальной версии записи. Доступны только переходы, разрешённые backend: новое → принято; принято → в процессе; в процессе → уточнение/выполнено; уточнение → в процессе; выполнено → закрыто или обратно в процессе; отклонение доступно на разрешённых этапах. В закрытом или отклонённом обращении отправка сообщений запрещена.

Назначение ответственного, срок выполнения, создание организаций, счета и общие документы остаются полномочиями администратора. Сотрудник не получает доступ ко всем данным арендатора только потому, что ему назначено одно обращение.

## Показания и защита доступа

Ответственный за категорию **Электричество** получает доступ к электрическим счётчикам; ответственный за **Водоснабжение и отопление** — к водяным. Это доступ по типу приборов в организациях, а не произвольный выбор области самим сотрудником. Остальные направления не получают доступ к показаниям без соответствующего назначения.

Фото выдаётся специальным защищённым маршрутом после повторной проверки направления. Принятие/отклонение доступно только для переданного, ещё не проверенного показания. Одновременные действия сотрудника и администратора не перезаписывают результат: выигрывает одна проверка, другая получает конфликт. Исходное значение и предыдущая отметка не меняются. Коррекцию базы делает только администратор.

После переназначения обращения бывший ответственный теряет доступ к карточке, её файлам и связанным уведомлениям. После смены ответственного направления теряется доступ к его показаниям и фото. Проверка выполняется сервером на каждом запросе; ранее загруженные в браузер данные нельзя физически отозвать с устройства, поэтому после изменений используйте обновление/выход из сессии.

Уведомления появляются для новых событий после включения этой версии; историческая переписка автоматически не превращается в уведомления. Открытие обращения отмечает доступные события этого обращения прочитанными. Центр уведомлений хранит отдельные отметки и не выдаёт события других сотрудников. При утрате доступа старые записи исключаются из выдачи, а не передаются новому ответственному автоматически; новое назначение создаёт новое событие.

## Ограничения и внешние системы

Битрикс, 1С, email, SMS, банковский шлюз и native push по-прежнему не подключены. Сохранённые обращения, ответы и показания не выдаются за доставленные во внешние системы. Письма для восстановления пароля не отправляются; до подключения почты нужно обращаться к администратору.

Токен хранится только в памяти. После обновления страницы нужно войти снова. Выход отзывает серверную сессию. Физические Android/iOS-устройства и production-развёртывание требуют отдельной проверки.

## Проверки

```bash
# Из корня репозитория
scripts/dev.sh test

# Из tenant-app-frontend
npm run typecheck
npm test
EXPO_OFFLINE=1 npm run build:web -- --clear
python3 scripts/verify-backend.py
```

Браузерный скрипт использует production-сборку, настоящее API и отдельную временную PostgreSQL. Наборы администратора, сотрудника и арендатора запускаются последовательно с перезапуском тестового API между наборами; рабочие лимиты запросов сохранены. Рабочая БД не изменяется. После тестов временная база удаляется, процессы останавливаются. Скриншоты — в игнорируемой папке `tenant-app-frontend/test-results`.

## Результаты проверки

5 ноября 2026 года: прошли 48 backend-тестов без пропусков, TypeScript и 20 frontend-тестов. Восемь браузерных сценариев прошли на настоящем API и отдельной PostgreSQL: три административных, три рабочих сценария сотрудника и два сценария арендатора. Проверены публичные/внутренние файлы, прямое скачивание, отзыв доступа, уведомления, фото, рассмотрение показаний, мобильная навигация и выход. Серверный тест конкурентного рассмотрения подтвердил единственный результат при одновременной проверке администратором и сотрудником. Миграции и новые внешние зависимости не добавлялись.
